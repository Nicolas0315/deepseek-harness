# Agent Note: 日文会话内容搜索

Status: implemented

[English](2026-10-14-japanese-session-search.md) | 中文

## 问题

SQLite FTS5 的 `unicode61` tokenizer 把没有空格的日文句子视为单个 token。因此搜索 `日本語` 会漏掉 `これは日本語の文章です`，尽管查询整句可以命中。会话内容搜索需要单字符和双字符召回、兼容假名匹配以及日文／拉丁文混合文本，同时不能改变拉丁文完整 token 匹配或权威 Session 日志。

## 决策

SQLite 查询提供方保留原始文本列，并仅为包含日文字符的文档增加索引中的日文投影。NFKC 规范化按源字素执行；日文字符成为独立的 FTS token，拉丁字母与数字串则保持完整。投影省略表意文字变体选择符。原始与投影的字面短语通过 OR 组合，并明确限定各自的列；两条分支都不会把调用方文本解释为查询语法。持久化文档与实时文档在现有的对账事务中同时写入两列。

排序取原始与投影列高亮出现次数的较大值，避免两列找到相同文本时重复计分。文档长度仍为原始码点数。摘要位置把投影匹配映射回原始字素，因此兼容展开、分解浊音符、补充平面字符与变体选择符不会把规范化字符或插入的分隔符泄漏到显示文本中。游标标识、世代变化、实时遮蔽与分页保留现有规则。

可丢弃索引使用单调递增的 schema 版本 9。现有所有权检查允许从 Session 数据重建已识别的旧版派生索引；Session 世代、事件类型、公共请求与响应字段均不改变。[包参考](../../../../packages/session-query/session-query-sqlite/README.zh.md)负责配置与搜索语义。

## 考虑过的替代方案

**用 trigram 替换 `unicode61`。** SQLite 的 trigram 全文查询无法匹配少于三个 Unicode 字符的文本，会排除 `日` 和 `日本` 等常用日文查询。统一替换还会改变拉丁文子字符串召回，包括 `BRAID` 内的 `AI`。

**把所有文档拆为字符。** 拆分拉丁文会改变现有的完整 token 与短语语义，并为纯英文历史倍增索引条目。把辅助列限制为日文文档可保留原始英文语料库及其排序。

**扫描全部文档正文。** 字面扫描避免了索引投影，但使每次查询的工作量与整个语料库成正比。索引候选检索保留现有的查询模型；只有匹配结果的摘要才需要原始位置映射。

**增加形态分析器。** 分词会引入词典和额外的语言相关运行时，却无法提供所需的任意短字符短语。读音转换与跨文字系统转写仍不属于此搜索行为。

## 影响

日文文档在对账时需要额外的索引文本与规范化工作。纯英文文档的辅助列保持为空。查询仍是同步 SQLite 操作；本决策不会消除该阻塞成本。投影扩大索引召回而不修改原始文本，并在混合文本中保留拉丁文完整 token 语义。

聚焦的投影与服务测试覆盖日文短语召回、单字符和双字符查询、半角假名、分解浊音符、补充平面汉字、变体选择符、原始摘要位置与拉丁文不匹配。真实 JSONL 集成测试覆盖持久化召回和索引重建，并检查规范源文件的字节保持不变。浏览器测试在日文设置下覆盖完整应用的内容搜索路径；其预期 UI 输出属于拥有该行为的 Web 测试，因为预置历史不构成录制 Session 的回放往返。
